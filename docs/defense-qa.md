# 第一部分：对手研究三问（口头版，合计约 2 分 40 秒）

## Q1 差距分析（60 秒）

> 我们的工程化是有底子的，场景只够一半，真实用户验证是零。

**工程化**：三条路由（补采 / 全绿跳过模型 / 离线直接停）每条都有测试锁定；11 条规则，3 条是组合型；6 个异常场景的规则集是精确相等断言，不是"看起来对"。

**场景**：每个分支都带传感器语义——帧间缺口判 degraded、空 buffer 或数据过旧判 offline、R03 是温度上升趋势这类领域规则。但我**说不出具体是谁在什么现场用**：缺一个可识别的设备和一类人。这是能力，还不是场景。

**真实用户验证**：一条都没有。demo 数据是构造的，模型和检索在测试里都是替身。这是最大的硬缺口，而且不是写代码能解决的，得去找人。

## Q2 三句话（45 秒）

> ① 场景：【某类设备】上的传感器读数异常，可能是设备坏了，也可能是传感器自己坏了、掉线了。现场最怕对着坏数据下判断。
>
> ② 不可替代：它不先让模型下结论，先判断这份数据能不能信——有缺口补采一次，离线就停下并说明原因，正常就不调模型。通用助手看不到数据质量，只能对着输入什么都答。
>
> ③ 工程化：一条管线、三份数据、三条路，每条结论都能追到触发哪条规则、引用手册哪一段。

## Q3 校准清单（60 秒，按"已修 / 未修 / 不迁"三档答）

**已兑**：offline 判 failed 并写明原因；demo 补上路径 C；竞态用 conftest 的 autouse fixture 治理（去掉 fixture 单跑 test_isolation 会 1 failed 1 passed，可稳定复现）；README 数字和仓库对账。

**未兑，写进已知限制**：补采结果为 offline 时未拦截——首采 degraded、补采时 buffer 被清空，会拿空读数继续走到 report，可能判 complete。没修就写没修。

**评估后决定不做**：langchain-community 迁移。核实过官方没有独立替代包——`langchain-classic` 里的 FAISS 是转发回 community，PyPI 上 `langchain-faiss` 0.1.1 是第三方空壳（wheel 1 KB、`__init__.py` 0 字节）。所以收口 + 钉版本，触发条件写在 docs 里。

**仍需你确认的**：degraded 阈值现在是按 30 秒采样间隔设的，DHT22 手册最短约 2 秒一次；真实设备的实测周期我还没有，这条要现场补。

# 第二部分：评委可能问（10 题）

| # | 问题 | 回答要点 |
|---|---|---|
| 1 | 为什么采样间隔 30 秒？ | `SAMPLE_INTERVAL_SEC=30.0`，帧数阈值都按它折算；DHT22 手册约 2 秒一次，30 秒对机柜这类慢变量够用。**真实周期未实测**，是已知待办。 |
| 2 | 准确率多少？ | 知识库问答有评测：20 题，Top-5 命中 85%，平均检索 0.026 秒。**诊断结论没有准确率指标**——因为没有真实故障标注，我们不编这个数。 |
| 3 | 为什么不把所有数据都丢给大模型？ | 三个理由：坏数据上模型会给假根因；全绿时调用只是花钱买一段可能编的话；模型调用意味着依赖网络。这三条都写在降级策略里，不是口头设计。 |
| 4 | 规则 11 条够吗？覆盖什么？ | 阈值、趋势、跳变、冻结、震荡、持续越限、阶跃越界；R09/R10/R11 是组合型。**跨传感器组合（温升+湿度异常）没做**，因为 state 现在是单 sensor_type，改契约牵动四个 Agent。 |
| 5 | 置信度 0.67 怎么来的？ | `数据质量权重 × (0.5 + 0.5 × min(引用条数,3)/3)`，公式写死在报告层，可当场复算——不是模型自己报的数。 |
| 6 | 离线时为什么不给个兜底结论？ | 给一个明确失败，好过给一个像模像样的猜测。状态 failed、错误列表写明"窗口内无有效读数"，下游规则/AI 都不运行。 |
| 7 | 和市面上的设备监控平台差在哪？ | 我们不做大规模实时流，也不做毫秒告警；做的是**告警之后为什么**——带溯源的单机诊断。FAISS 是静态的，知识不会自己更新，这是限制。 |
| 8 | 数据存哪？隐私怎么办？ | 向量库和采样 buffer 都在本地，除了 DeepSeek 的模型调用不出网。全绿和离线路径完全不联网。 |
| 9 | 一个人做的？怎么保证质量？ | 214 条测试（管线 112），先红后绿；路由、规则、降级都有用例锁；依赖用最小安装验证过（全新 venv、不装 ML 栈，demo exit 0、agents 112 passed）。 |
| 10 | 如果现在上线，第一件事做什么？ | 不是加功能，是标定阈值：拿真实设备的采样周期和故障数据，把 30 秒和那几个阈值重算一遍。现在这些数是从手册和构造数据来的。 |

# 第三部分：面试官可能问（5 题，问的是"人"）

| # | 问题 | 回答要点 |
|---|---|---|
| 1 | 这个项目里最难的是什么？ | 不是写管线，是**判断什么该让模型说话**。补采只补一次、全绿不调模型、离线直接停——三条都是"少做事"的决定，每条都要能说清代价。 |
| 2 | 你负责哪部分？ | 全部代码（AI 辅助），但设计决定是我做的：路由契约、规则清单、降级策略、测试策略。AI 写的每一段我都跑过、改过、写过测试。 |
| 3 | 怎么用 AI 又不被它带偏？ | 三条纪律：先写测试再让它实现；每个数字必须来自真实输出（README 的数字错一次就被抓过一次）；拿不准的事实（比如那个第三方包是不是官方的）必须去查证，不能信描述。 |
| 4 | 你最大的失误？ | 有一次把"想起来要跑"当成"已经跑了"，输出接管道后 GBK 崩了、退出码 1，我当成功贴出去了。后来所有留档都先看退出码。 |
| 5 | 如果重做一次？ | state 一开始就设计成多传感器，跨传感器组合规则现在就做得动；另外先去找一个真实用户，而不是先把管线写漂亮。 |

# 第四部分：不要说的话（红线）

- ❌「准确率 90% 以上」——没有这个数，也测不出来。
- ❌「已经在某某工厂用了」——没有。
- ❌「支持所有传感器」——写死了 temperature / humidity，vibration 只在采集层。
- ❌「完全不怕断网」——只有全绿和离线路径不联网，规则触发后的 AI 分析要联网。
- ❌「迁移到 langchain 新包了」——评估结论是不迁，别顺口说成迁了。
